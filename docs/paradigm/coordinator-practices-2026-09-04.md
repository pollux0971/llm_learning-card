# 我這幾天自己發明、範式沒寫的做法

格式:**做法** → 為什麼好 → 能不能抄進模板。

---

## A. 工單(這是最大的一塊)

### A1. 固定七段結構
**做法**:每張工單一定有這七段,順序固定 ——
`第一步`(pwd + branch + git log 確認位置)→ `鐵則`(硬規則,最重要的放第一條)→ `開工前讀`(檔案清單,能給行號就給)→ `要做的東西` → `測試要求` → `驗收`(編號,每項附**預期數字**)→ `交付要求`(P-29/P-35/DoD)→ `回報`(要它講什麼)。

**為什麼好**:worker 不用猜「做完」是什麼意思。**驗收附預期數字**(「vitest 應該 1508 全綠」)讓「我跑過了」變成可查證的 —— 它報 1508 我知道它真的跑了,報「全綠」我就得自己再跑一次。

**抄進模板**:可以,`template/TICKET.md` 一個空殼 + 一個填好的真實範例。**範例要用真的工單**,不要寫教學用的假例子。

### A2. 開頭寫「這個 bug 是怎麼被發現的」
**做法**:每張修 bug 的工單都寫真實情境,例如「真的跑一次 29 張卡的文章才發現,`sec-0022` 少了考題檔,但 log 沒記、CLI 沒印,只能事後數檔案才發現」。

**為什麼好**:worker 知道**失敗長什麼樣**,判斷會不一樣。實證:golden set 那張,worker 發現資料結構裝不下五組時**沒有硬湊**,它的理由直接引用了工單裡「改了 prompt 沒人發現品質變差」那句。如果工單只寫「登記五組」,它大概會交出三組。

**抄進模板**:可以,列成工單必填欄位 `## 這個問題是怎麼被發現的`。

### A3. 我的每個轉述都標【推】
**做法**:凡是我從技術顧問那邊轉述的技術前提,工單裡明寫「**那是【推】,你實測**」。

**為什麼好**:**這一條抓到了兩次模板迴歸**。兩次的觸發語句都是「我跑過,跟 main 一模一樣」,兩次都是假的。如果工單寫成事實,worker 會直接同步,我們會靜默失去 16 條落點設定、兩個旗標、四個排除目錄。

**抄進模板**:**強烈建議**。而且要寫成「**協調者轉述的一律預設【推】**」,不是「必要時標」—— 預設值要站在懷疑那邊。

### A4. 「不要為了讓它綠而 ⋯」條款
**做法**:每張工單都有一句,明白寫出**那個誘人的錯誤動作**。例如:
- 「不要為了讓它綠而放寬規則或刪場景」
- 「模板版誤報就是模板的 bug,**不要遷就它改 `docs/`**」
- 「不要為了湊出 4 對去調閾值」

**為什麼好**:那些動作都**很合理**,而且能讓工單收掉。事先點名,worker 撞到時會認出來。實證:doc-links 那個 worker 明確回報「**我沒有改 `docs/`**」—— 它知道那是被禁止的選項,而不是沒想到。

**抄進模板**:可以。做法是**每張工單想一次「最快讓它變綠的作弊路是什麼」然後寫出來**。

### A5. 指定「你要親手搭這個情境」
**做法**:不寫「驗證 X」,寫「**自己在臨時目錄搭一個巢狀 repo:外層是 repo、`learning/` 不是 → snapshot 必須退出 1,而且外層 repo 的 HEAD 與工作區完全沒有變化。把指令與輸出貼給我**」。

**為什麼好**:「驗證 X」會變成看一眼測試綠。指定情境 + 要求貼輸出,會變成證據。實證:那個 worker 不只驗了正確版,還**反向換成錯誤寫法確認卡片真的會被 commit 進外層 repo**。

**抄進模板**:可以,寫成「危險項要指定情境與**要求貼指令與輸出**,不要只寫『請驗證』」。

## B. 審核輪

### B1. 「逐項列前提,各自實測」
**做法**:審核工單把要驗的前提**逐條列成清單**,每條要求獨立實測並貼輸出。不是「確認同步沒問題」,是「`--root` 在不在?`--manifest` 在不在?三支的 0 條目守衛各跑一次?`tmp-learning` 清理放個 marker 進去看會不會被清?」

**為什麼好**:整體性的「沒問題」會漏掉「綠著掉功能」。實證:模板 1.2.0 那次,**三個 headline 都真的修好了、跑起來全綠**,但掉了四個排除目錄 —— 只有逐項比才看得到。

**抄進模板**:可以,而且**這是三次同型問題的共同解**。

### B2. 「再試幾個我沒提到的形狀」
**做法**:審核工單固定加一句 ——「除了上面列的,**自己想幾個 commit message 沒提到的形狀去試**」。

**為什麼好**:只驗作者想得到的,等於讓作者自己出考卷。實證:P-28 的審核 agent 額外試了 **11 種**巢狀圍欄(四反引號、未閉合、inline code 裡的 `](`、`~~~`),全部正確 —— 那 11 種沒有一種在我或開發 agent 的清單裡。

**抄進模板**:可以。

### B3. 開發的每個判斷都要「哪個測試會紅」
(這條後來變成 P-29,但**它是從我工單裡長出來的**,記一下來源。)

**做法**:要求開發 agent 自己列判斷,審核輪**逐一手動破壞**。後來我在開發工單裡加了一句:「**你自己先想想『如果有人把我這個判斷改掉,哪個測試會紅?』答不出來的就在回報裡講**」。

**為什麼好**:把發現時機從審核輪往前挪到開發輪。實證:phase-4 那個開發 agent **自己列了三個答不出來的缺口**,其中一個是**它剛寫的核心修法沒有測試能證明改對了**。以前這要等審核輪破壞才會浮出來。

**抄進模板**:可以,而且值得分成兩句 —— 開發輪的自問句、審核輪的破壞句。

### B4. 數字要重算,不要抄
**做法**:審核工單要求「**自己重算一次 ADR 裡的數字**,對不上就是編的」。

**為什麼好**:實證抓到 ADR-043 兩個編造的數字(72 應為 75、34 應為 33)。那份 ADR 的**全部價值就在數字**。

**抄進模板**:已經是 P-15 的補充了。

## C. 協調者自己的做法

### C1. 我出錯時,明說「我工單寫錯了,照你實測的」
**做法**:worker 的實測跟我的工單衝突時,回覆第一句就是「**你對,我工單寫的錯了**」,然後才講怎麼做。

**為什麼好**:worker 要能**相信現實勝過工單**,而那需要明確授權。實證:12/phase-2 那張我寫錯兩個基準(重複率 4 對、圖形狀 1 筆),worker 兩個都實測推翻。如果我第一次含糊帶過,第二次它可能就照工單寫了。

**抄進模板**:可以,寫成協調者的行為規則。

### C2. 被卡住時,切分「跟版本/決策無關」的部分先做
**做法**:worker 卡在等外部東西時,明確切兩批:「現在做這些(跟版本無關)、等通知再做這些」,並說「**做完第一批就回報並停,不要為了收工去 skip 或放寬任何東西**」。

**為什麼好**:空等浪費,但「為了收工而妥協」更貴。把停止點講明就不會二選一。

**抄進模板**:可以。

### C3. 改變方向時開新工單 + 標舊的 superseded 附理由鏈
**做法**:技術顧問三次改變模板採用方法(手抄 → 指向模板路徑 → sync 腳本),我**開新工單、把舊的標 superseded 並寫下理由鏈**(「v1.0.1 指向模板路徑,CI 沒那條路,撤回」),而不是編輯原工單。

**為什麼好**:一小時後我不會憑記憶重建,而且**下一個人看得到那兩條路為什麼被否決**。

**抄進模板**:可以。

### C4. 成本當一等公民
**做法**:每輪回報第一行有 `今日花費 $x.xx / 1.00`;審核輪的 $ 與時間我會記(這輪 84/45/40 分、$10.4/$8.5/$6.8)。

**為什麼好**:**看到成本才會看到浪費**。三個 Stryker 互相 OOM 那次,如果我沒在看時間與 $,只會覺得「今天比較慢」。看到 $25 燒在互相踩踏,才會去改派工規則。

**抄進模板**:可以 —— 回報格式已經有花費,建議**加上審核輪的耗時與成本**。

### C5. 長訊息先寫檔再 `--body "$(cat 檔案)"`
**做法**:含反引號、`$`、括號的訊息一律先寫檔。

**為什麼好**:我踩過兩次 shell 展開把訊息弄壞(一次還誤發了一則垃圾)。worker 也踩過一次。

**抄進模板**:進 PITFALLS,一行。

## D. 範式裡我刻意不遵守的

### D1. 我不跑 `/phase-done` skill,把檢查直接寫進審核工單
**為什麼**:那個 skill 是給互動用的,而我的審核工單**比它嚴**(它沒有反向驗證、沒有「逐項列前提」、沒有 P-29 破壞驗證)。跑 skill 會給人「驗收過了」的感覺,但實際比較弱。

**建議**:要嘛把 skill 補到跟工單一樣嚴(我已經加了 `lint:docs` / `accept:dry` / P-42 那三段),要嘛在 skill 裡寫明「**這是互動用的最小集,派工驗收用工單模板**」。現況兩者強度不同但沒人說,那本身就是坑。

### D2. 我不用 `/decide`,讓 worker 在自己的工單裡寫 ADR
**為什麼**:ADR 的價值在**細節與數字**,而那些只在剛做完的 worker 腦子裡。我事後用 `/decide` 寫,會寫成一段空泛的「我們決定用 A」。

**代價**:worker 寫的 ADR 有可能編數字(ADR-043 就是),所以要配 B4(審核輪重算)。

**建議**:模板改成「**ADR 由做的人寫、審核的人重算數字**」,`/decide` 留給協調者自己做的決定。

### D3. 我沒跑過 `npm run lint:wiki`,也沒寫 sprint 檔
**為什麼**:老實說是**一直有更急的事**,維護清單第 3、6 項從來沒輪到。

這不是好理由 —— 我應該至少跑一次 `lint:wiki` 看看使用者的 25 張卡有沒有結構問題。**下一輪空檔補**。

**建議**:維護清單的項目如果連續 N 輪沒被碰過,應該升級成一張工單,不然「有空再做」等於不會做。

### D4. 我把「審核輪一次只派一個」加進去了(現在是 §2.3)
這條原本沒有,是三個 Stryker 互相 OOM 之後我自己加的。記一下**它是事後補的**,代表原本的「worktree 上限 3」只管數量不管性質。

## E. 三次同型問題的完整形狀(建議寫成一條)

| 次 | 東西 | 症狀 |
|---|---|---|
| 1 | scanner 掃到 0 個檔 | exit 0,「看起來很乾淨」 |
| 2 | golden registry 只有 demo | 框架完美,守著假資料 |
| 3 | registry 的 key 型別 | `children.md` **不可能**被單獨守著 |

三個都長成「**東西在、綠的、但沒在守**」。P-42 目前寫了前兩個變體,**第三個(資料結構容不下)是新的**,而且最難發現 —— 前兩個是「忘了填」,第三個是「填不進去」。

**建議的驗收問句(三段)**:
1. 這東西現在守著哪些**真實對象**?列出來。
2. 有沒有哪個對象**列不出來**?(忘了填)
3. 有沒有哪個對象**這個資料結構根本表達不了**?(填不進去)
