# `docs/reviews/` — 交接與審核紀錄放哪裡

## 一句話規則

**進行中的交接 = `.orca-brief/REVIEW.md`(gitignore,worktree 專屬)。
做完的一輪 = `docs/reviews/<分支名>-<用途>.md`(進版控)。
repo 根目錄永遠不放 `REVIEW.md`。**

## 為什麼有這一頁(P-78 的第三次)

根目錄的 `REVIEW.md` 被三輪不同的 worker 各寫了一次,每次都覆蓋掉上一輪的紀錄。
前兩次的處理是「搬走 + 再寫一份警告」。**警告寫到第三次就代表寫警告本身沒用,要改結構。**

第三次還多暴露一件前兩次沒看到的事,值得記下來:

2026-09-12 協調者把 main 上根目錄那份搬進本目錄之後,**兩條各自在自己 worktree 用同一個
根目錄路徑寫交接的分支**(`lock-orphan`、`env-probe`),`git merge main` 時都被 git 的
**改名偵測**認成「同一個檔的兩個版本」——**兩份完全不相干的交接直接內容衝突**。
同一天撞兩次。

所以這個路徑的問題不只是「上一輪的紀錄會被蓋掉」,是**它會讓兩條互不相干的工作線在合併時
互相絆倒**。這是結構問題,不是紀律問題。

## 搬檔案的時候會踩到的一件事

**連結掃描器不分「引用」與「說明」。** `lint:docs` 會驗 backtick 裡「路徑:行號」形式的參照,
而那種參照是**相對於檔案本身**解析的 —— 從根目錄搬進本目錄,原本對的路徑就失效了。

實際發生兩次:

1. 搬完就紅一次(檔內原有的參照失效)。
2. 改好之後,協調者在搬遷註記裡**解釋**那條路徑時又打了一次同樣的字面 —— **再紅一次**。

第 2 次是掃描器對的行為,它讀不到你的意圖。**規則:搬檔案時,註記裡提到舊路徑要寫成
不可解析的形式** —— 拿掉 backtick,或寫「原本在根目錄」而不寫路徑字面。

## 命名

`<分支名>-<用途>.md`,例如:

- `lock-orphan-review.md`
- `template-141-adoption-handoff.md`
- `03-llm-router-phase-2-round-1.md`

歷史檔沿用舊名字不改 —— **那些寫的是「當時」的狀態,改掉等於竄改紀錄。**
只有「現在還在用的設定與指示」才更新。

## 新規則上線時,存量資料怎麼辦(過渡條款)

> **新規則上線時,既有的條目一律標「規則生效前,無此欄位」,不准回填推測。
> 只有重新量過的才填實數。**

為什麼要單獨寫一條:**規則上線的那一刻,存量資料全部是不合規的**,而人的第一反應是
把存量補成「看起來合規」,不是承認它不合規。新規則要求的資料,對**已經發生過的事**
根本不存在;想合規,唯一的路徑就是回頭取一個取不到的數 —— 推測就從那個縫隙鑽進來。

### 實例:規則作者第一次就守不住自己的規則

2026-09-12,協調者立了一條規則:「寫逾時 / 重試 / 等待的理由時,一定要一起記當下的機器負載」。
**在寫這條規則的同一個 commit 裡**,他給三個既有的效能數字補了一句「今天空機 `uptime` 負載 < 1」
—— **那句沒量就寫**。真的去跑 `uptime` 的時候 load average 是 12.47。

而且更根本的問題是:那三個數字是幾小時前量的,**當時沒記 uptime,事後也重建不回來**
(load average 是衰減平均,查不到過去式)。

誠實版長這樣,可以直接照抄形狀:

- 明說**哪些數字沒有這個欄位**,以及為什麼(「這條規則就是這次才立的」)。
- 只寫**確定知道的**(「只能確定當時沒有 worker 也沒有 Stryker 在跑」)。
- **單獨列出有量過的那一次**,標清楚它是補量的。
- 承認**還沒量到的形狀**,讓退出條件變成真的待辦而不是形式。

### 這條管過去,另一件事管未來

過渡條款管的是**存量**:規則生效前的條目標「無此欄位」,**不准回填推測**。

管**未來**的是另一個做法 —— **易逝的觀測由工具在產生輸出的同一刻自動蓋章,不寫成給人遵守的規則。**
守門的機器可讀標記行行尾加 `load=<os.loadavg()[0]>`,不依賴任何人記得:

```
gate=boundaries result=PASS scanned=211 load=5.74
```

為什麼非得是工具蓋章:`load average` 是衰減平均,**過去式查不到**。漏記不是「等等再補」,
是**永久遺失**,而且**漏記長得跟「不適用」一模一樣**,沒有任何事後檢查抓得到。

**兩條合起來才完整**:過去的誠實標記為空,未來的結構保證有。
**只有需要判斷的東西才交給人。**

## 通則:任何「暫時這樣」都要寫退場條件

2026-09-12 一天之內,**同一條規則以四種不同的載體出現**,所以它不是個案:

| 載體 | 實例 |
|---|---|
| **逾時放寬** | `degraded-report.test.ts` 的 30s:退場條件 = 「鎖自證死活做完、重量一次,p95 < 2s 就收到 10s」 |
| **TODO 的狀態宣稱** | 「這一整組現在是紅的」—— 實作補上之後那三句躺了好幾週,**沒有守門會告訴你它過期了**(測試從紅變綠是好事,好事不會觸發警報) |
| **暫時放寬的規則** | 待覆核的 ADR、標「先這樣」的 gate 例外 |
| **自救設定(workaround config)** | `scripts/gates.config.json` 的 `skipDirs` —— 見下 |

> **任何「因為現在如此,所以暫時這樣」的東西,都要寫退場條件,而且退場條件要是一個
> 可查的事實(某版修好、某張工單做完、某個數字達標),不是「等有空」。
> 沒有退場條件的暫時措施,壽命會超過它描述的那個「現在」。**

  **自救**,因為模板 `_root.ts` 的 `DEFAULT_SKIP_DIRS` 在 **1.6.1 以前**漏了它。

  而沒有人會記得回來看。
- **`skipDirs` 的 `tmp-learning`** —— **不是自救,是我們自己的**測試輸出目錄,**永久保留**。

`_root.ts` 的 `resolveSkipDirs()` 回傳的是 `Set<string>`,**逐字比對目錄名**。寫 `learning-*` 進去

所以 `.gitignore` 裡的 `learning-*/`(多類別測試輸出)**目前仍然會被掃到**,是一個尚未修掉的
分母漂移來源。要嘛模板支援 glob,要嘛測試不要產生名字會變的目錄。

## 升版單開始執行後,目標版本凍結

> **升版單一旦開跑,目標版本就凍結。期間上游出的新版,除非修的是我們正在踩的東西,
> 一律排下一批。判準是一句話:「不升這版,我們現在會壞嗎?」答案是「不會」就不追。
> 收斂比最新重要。**

來由(2026-09-12,同一天):`template-161` 那張的目標從 **1.6.1 → 1.6.2** 已經改過一次
(上游修了我們正在踩的 `.stryker-tmp` 漏排除)。接著上游又出 **1.6.3**,修的是
「`skipDirs` 含 glob 要硬錯」—— **我們已經沒有 glob 項目了**(那個假設定當天就拿掉),
所以升不升行為完全一樣 → **不追,排下一批**。

**每次改目標都是重新 sync、重新量、重新驗。追一個移動中的目標不會收斂。**

### 例外要指名它是哪一條例外

同一天 `accept:coverage` 因為 1.6.0 的段一不排除 `todo` phase 而紅了 16 個檔,
那時的判斷是**追 1.6.4**。看起來跟上面矛盾,其實不是 —— 判準那句話的答案在這裡是
**「已經壞了」**,正好落在規則自己寫的例外裡。

**規則有例外不等於規則鬆掉,關鍵是例外要指名它是哪一條例外。**
說「這次情況特殊」不算;要能指著規則裡的那半句說「我引用的是這個」。

## 「依狀態放寬」的守門,兩條反向驗證都要做

一道守門如果會**依某個狀態放寬標準**(例如 `todo` 的 phase 不檢查 undefined),
**只驗嚴的那一邊不夠**:

- **(甲)嚴的那條路還嚴**:把狀態改成嚴格的那一種 → **必須紅**。
- **(乙)寬的那條路是「放寬」不是「沒跑」**:把狀態改成放寬的那一種 →
  **必須仍然有在跑,只是標準不同**(輸出要看得出它比對到了東西)。

> **放寬路徑的陽性對照,必須證明它「有在跑,只是標準不同」,不是「沒在跑」。**

理由:**兩者在綠燈上長得一模一樣。** 一個「整段被跳過」的守門與一個「依狀態放寬」的守門,
輸出都是綠的;只有 (乙) 分得出來。

實例(2026-09-12,`check-phase-coverage.ts` 的 1.6.4 修法):
段一改成依 `FEATURE.md` 狀態決定要不要檢查 `undefined`。
只做 (甲) 的話,萬一段一其實整段沒跑,測試一樣會通過。

## 反向驗證是對照實驗:一次只改一個變數

> **反向驗證是對照實驗:一次只改一個變數,其餘逐字不動。**
> 「改狀態」與「換一個不同內容的檔案」是**兩個**變數 —— 綠變紅就不知道是哪個造成的。
> 正確做法是**同一份注入、同一個檔案,只切換那一個變數,跑兩次**。

### 這條是三個人接力補出來的,所以更該寫下來

2026-09-12,`check-phase-coverage.ts` 的「依 phase 狀態放寬」修法要驗:

1. **技術顧問**要求:「`todo` → `done` 必須紅」。
   —— 只驗了**嚴**的那一邊,證明不了寬的那邊是「放寬」還是「整段沒跑」。
2. **協調者**補:「反過來也要驗,`done` → `todo` 要從嚴格變略過」。
   —— 方向對了,但**動了兩個變數**:狀態變了,而且換成一個原本就乾淨的檔案。
3. **worker** 指出第 2 點證明不了什麼(`done` 的 phase 本來就 0 undefined,兩邊都會綠),
   改成:**在一個原本乾淨的 `done` phase 注入一個沒定義的句子,同一份注入在兩種狀態各跑一次**。
   `todo` →「21 個場景(狀態=todo,undefined=1 不算)」PASS;`done` →「undefined=1」FAIL。
   **同一個檔、同一個注入,只差狀態,綠變紅。**

**三層各補一次,而且每次都往更嚴的方向 —— 但那是運氣,不是設計。**
三個人都沒有明確持有「只改一個變數」這條規則,所以只能靠接力。**寫下來,下次第一個人就會做對。**

### 同一家的另一條:陽性對照用歷史上真的有 bug 的 commit

(來源:`nightmare-assault`,2026-09-12)新守門的陽性對照,**對 `git show <當時那個壞 commit>:<檔>` 跑**,
要求它紅並指名位置 —— 比塞假資料強一級,因為它證明的是「**當時有它就會擋下來**」。

附帶那個坑也要記:他們第一版的 self-test 自己炸掉,**主掃描照樣印「0 處違規」** ——
**self-test 失敗必須讓主輸出也紅**,否則它就是一個「壞掉時看起來乾淨」的掃描器。

**兩條是同一個問題的兩半:你的綠/紅能不能歸因?**
「只改一個變數」管的是**紅的歸因**;「用真的壞 commit」管的是**綠的歸因**。

## ⚠️ 一個保護機制要問四次「作用在什麼上面」

2026-09-12 一整天,**同一個保護機制(每日花費上限)在四個不同的作用點上失效,
而四個都長得像同一個問題:「煞車沒接上」。**

| # | 問題 | 早上 | 收工時 |
|---|---|---|---|
| 1 | **呼叫**有沒有進帳本 | ❌ `createFileLogAppender(undefined)` 靜默丟棄 | ✅ 沒有 log 就硬錯(ADR-050) |
| 2 | **帳本**有幾份 | ❌ 每個 worktree 一份 | ✅ 單一,`git-common-dir` 解回主簽出(ADR-051) |
| 3 | 帳本**活不活得下去** | ❌ worktree 一清就沒 | ✅ 進了 vault 的版控 |
| 4 | 上限**保護什麼** | ❌ 一個簽出 | ✅ 使用者的錢包 |

⚠️ **如果早上只修第 1 個就宣告完成,`llm-spend` 會開始回真數字 —— 而那個數字仍然是錯的。
那比回 `$0.0000` 更危險,因為它會被相信。**

> **所以這一批的教訓不是「要記帳」,是:一個保護機制要問四次「作用在什麼上面」——
> 呼叫、帳本、壽命、保護對象。**

**我們是一次撞一個撞出來的。那四個問題應該變成清單,而不是四次運氣。**

**這是「作用點」那條規則(選任何作用工具前要確認工具端與問題端)在**同一個機制上連續失效四次**的實例
—— 前面幾次是「一個工具配錯一個問題」,這次是「一個問題有四層,而我們每次只看見一層」。**

### 同一天的兩個佐證(它們讓「四層」不是事後編的)

- **變異分數**:`mutate.ts` 誠實地寫檔、`.gitignore` 誠實地忽略產出、worktree 清理誠實地刪整棵樹
  —— **每一步都對,而結果是分數留不下來。**(第 3 層:壽命。)
- **帳本**:每個簽出的 `llm-spend` 都誠實回報「未達上限」,**沒有任何一個在說謊,但加起來超過。**
  (第 4 層:保護對象。)

**兩個都是「所有部分都說真話,而總和是錯的」—— 分割造成的錯誤不會觸發任何警報,因為每一塊都是對的。**

## 2026-09-12 磨出來的其餘規則(按用途分組)

### 讀與寫:名字與範圍

- **名字是對「用途」的承諾,從來不是對「範圍」的承諾。**
  要找的不是描述,是**定義域**,而定義域一定有落腳處:**主鍵 / 型別簽章 / 輸入 glob / schema**。
  **那四個位置之一會告訴你它裝得下什麼,檔頭的散文不會。**
  (實例:`known-defects` 真的裝已知缺陷 —— **只裝 cucumber 場景的**,主鍵是 feature 檔 + 場景名。)
- **轉述不要升級精確度。** 來源說「記憶體不夠」就寫原文,**不要翻成「OOM」** ——
  那個詞憑空帶進整套機制(核心 oom_killer / SIGKILL / `dmesg` 有紀錄 / swap 先被吃光),
  而**別人會拿你加上去的那部分去驗**。
  ⚠️ 代價不只是白驗:**對方會得到一個「有根據的錯誤結論」,比沒結論更難推翻。**
- **標籤是給「不讀內容的人」看的,所以它必須自己就是對的**,不能靠「內文有寫清楚」補救。
  **「內文有寫」是對會讀的人的補救,而標籤的受眾定義上就是不讀的那些。**

### 選工具與開單

- **選任何「作用工具」(gate / 登記表 / 旋鈕 / 工單)之前,兩端都要確認:**
  **(a) 這個工具實際作用在什麼上面?**(打開它看主鍵/型別/輸入範圍)
  **(b) 我要治的東西,質量實際落在什麼上面?**(量,不要推)**兩者同一個才動手。**
  ⚠️ **兩端查法不同,只查一端會漏掉另一端的錯,而兩種錯在「我選了一個工具」這個動作上長得一樣。**
- **開單前不要問「這個東西存在嗎」,要問「離它最近的既有東西是什麼?為什麼那個不夠?」**
  前者的回傳值是「無」,**而「無」感覺像結論**;後者永遠不是空的。
- ⚠️ **「我列出了幾個可行方案」≠「我找過最近鄰」。** 可行方案從**你想到的做法**長出來;
  最近鄰從**既有的做法**找出來。**判別:每個選項都要付代價嗎?三個都要付,
  通常代表你在自己的想像裡打轉 —— 既有的做法之所以既有,常常是因為它已經把代價解掉了。**
- **改同一段設定檔的工作,不分兩張單。**(判準相同只是「可以併」;同一段設定檔是「必須併」。)
  ⚠️ `.gitignore` 比 JSON 更糟:**JSON 的重複鍵至少是掃得出來的性質,
  `.gitignore` 的錯是語意上的 —— 順序影響結果,而錯的版本長得完全正常。**
- **排隊中的工單也會腐爛,派之前重新估一次。**
  ⚠️ **「重估」聽起來像「決定做不做」,最常見的結果其實是「還要做,但要做的不是原本那件」。**

### 驗證與歸因

- **反向驗證是對照實驗:一次只改一個變數,其餘逐字不動。**
- ⚠️ **「一次只改一個變數」管**紅**的歸因;「結論裡的每個 X 都要有『拿掉它會壞』的證據」管**綠**的歸因。**
  **紅的歸因錯,下一個人查下去會發現;綠的歸因錯,沒有人會去查(綠燈不會被複驗)** ——
  代價是**一份會被引用的假知識,而且它長得像實測結果,因為它確實是跑出來的。**
- **「依狀態放寬」的守門要兩條反向驗證**:嚴的那條還嚴 ✓;**寬的那條要證明「有在跑,只是標準不同」**,
  不是「沒在跑」——**兩者在綠燈上長得一模一樣。**
- **間歇性失敗找不到對應變數時,反過來問「它憑什麼會成功」。**
  找不到讓它成功的機制 = 成功是運氣 = **從來沒有正確過,只是常常沒被抓到**。
- **「還有一種情況沒驗」先問那種情況比已驗的更嚴還是更寬。** 缺更寬的不影響結論,缺更嚴的才要擋。
  ⚠️ **那是方向判斷,不是通行證。**
- **假設也要有退場條件,而且要綁在「本來就會發生的事」上。**
  ⚠️ **需要另外安排才會發生的檢驗,等於沒有退場條件** —— 而且它會長得像「我有留驗證計畫」。

### 訊號與觀測

- **選訊號時先問「它量的是什麼」,不是「它好不好取」。**
  同日三次:記憶體看 `free`(該看 `available`)、worker 死活看 mtime(該看程序 ——
  **mtime 測的是有沒有在寫,不是有沒有在做**)、假紅看 `load`(該看「同時幾組 vitest」)。
  ⚠️ **三個方便的數都「大致上會動」,所以才騙得了人 —— 會害人的永遠是「相關但不是它」的那個。**
- **量環境的 gate 要蓋「主體」欄。** 理由要用**綠**那支:
  **主體錯誤在紅的時候只是誤導,在綠的時候是偽證,而偽證不會被複驗。**
  粒度隨對象:檔案→路徑、機器→hostname、程序→pid、端點→URL、帳號→哪個 key。
  ⚠️ 判準:「**這個東西可能是別的,而值看起來一樣**」。
- ⚠️ **看守門輸出不要用 `tail`** —— 要看全,或 `grep -nE '⚠|✗'`。
  **`tail` 給你的是「最後幾行」,而守門的壞消息在中間,好消息(摘要)才在最後 ——
  `tail` 在結構上偏向讓你看到好消息。**
- ⚠️ **被環境砍掉的跑,會偽裝成一條有技術原因的紅。**
  實例:`✗ (exit SIGTERM)` 下面那行「執行/解析失敗:輸出裡找不到 "N scenarios"」
  **讀起來像解析 bug,實際是子行程被砍後的殘骸。**
  **沒有資訊的失敗至少長得像沒有資訊;這個長得像一條可以去修的 bug。**
  判準:**看到「解析失敗/找不到某字串」先往上找那一步是 exit code 還是 signal。**

> **「寫下來」的感覺像「學會了」,但那是兩件事。**
> **新規則上線後的頭幾天,要特別檢查「規則作者自己的產出」——

> **「描述一條規則」和「服從一條規則」用的是不同的注意力,而它們在同一段文字裡搶同一秒。**
> 寫的人整個注意力在「這句話講清楚了沒有」,而規則要作用的對象是「我此刻正在做的動作」——
> **那個動作在寫的當下是背景。**

**可執行版本:**

> **新規則或新建議落地的那個 commit / 工單 / 訊息,寫完之後把自己剛寫的東西
> 當成「別人的產出」讀一遍,只問一個問題 ——「這份東西違反了它自己剛立的規則嗎?」**

⚠️ **關鍵不在「再讀一遍」,在「當成別人的產出」。**
那一下把自己從作者切換成讀者,背景才會變前景。
**只寫「寫完檢查一次」的話,人會用作者的眼睛檢查,而作者的眼睛看不見那個。**

### ⚠️ 正確的輸出從來不會被稽核

2026-09-12 兩次「用錯的方法得到對的答案」:

| 方法 | 這次的結論 | 方法的毛病 |
|---|---|---|
| `tail -8` 看守門輸出 | 剛好對 | 漏掉中段第 29 行的 `⚠` |
| `grep -rnE "scanned=[^']*\$"` 找危險斷言 | 剛好對(安全) | **十行命中全是假的** —— `$` 在 regex 是行尾錨,在 `${scanned}` 是字面。**查詢找到的是自己的語法歧義** |

**共通點不是運氣好,是:答案對了,所以沒有任何訊號會響,所以方法被留下來,下次用在別的地方。**

**所以方法的稽核不能用結果觸發。**「答案錯了沒有」問不出來。要問的是:

> **「這個方法有可能給我錯的答案嗎?」**
> 不是「它這次錯了嗎」,是「它**有沒有能力**錯」。
> **有能力錯而這次剛好沒錯,方法就不能留。**

⚠️ **第二例的自證性要單獨記:那十行「長得完全像真命中」** —— 有行號、有那個字串、數量合理。
**停下來是靠「每一行都是 `console.log`」,也就是靠內容不對,不是靠數量不對。**
如果那十行剛好混進兩三個測試檔,就會停在一個對的結論上,**然後把錯的方法留下來**。

**處置:量的方法有歧義的時候,直接量結果。** 跑 `check-all.test.ts` 是用一個**跟那個 grep 完全無關的機制**
在問同一件事 —— 那不是「更仔細地 grep」,是**換一個獨立來源**。

**這也是「貼指令」那條規則的真正理由,請替換掉舊的:**

- ❌ 舊理由(想當然):可追溯、可重現
- ✅ **真正的理由:結論對的時候,指令是唯一還會露餡的東西。**
  兩次都是審核方**看指令、不是看結論**才發現問題的。

### 程序「沒有回應」的三態,一個 `ps` 就分得開

2026-09-12:審核方的 `check:phase-status` 15 分鐘不印東西,判斷是「第三次被環境砍掉」。**不是。**

```
$ ps -o pid,etime,time,pcpu,stat -p <pid>
    PID  ELAPSED     TIME %CPU STAT
2939885    05:10 00:00:00  0.1 Sl        ← 五分鐘,累計 CPU 時間 0 秒
$ cat /proc/<pid>/wchan
ep_poll
$ pgrep -aP <pid>
npm exec cucumber-js --tags @lint and @phase-1 --format summary
```

| 觀察 | 狀態 | 處置 |
|---|---|---|
| **沒有那個 pid** | 被砍 | 查三層:核心 OOM / 執行環境看門狗 / 程式自己的逾時 |
| 有 pid、**`TIME` 在漲** | 慢(被搶 CPU) | 等,或降併發 |
| 有 pid、**`TIME` 是 `00:00:00`**、`wchan` = `ep_poll` / `do_wait` | **在等子行程** | `pgrep -aP <pid>` 數子行程,**乘以單次耗時得到預估** |

**`TIME 00:00:00` 是那個判別式** —— 被搶 CPU 會累積 CPU 時間,等待不會。**一行就分開了「慢」與「等」。**

⚠️ **第三格的價值不只是診斷,是預估。** 38 × 60 秒 ≈ 38 分鐘 ——
**對方因此知道該等還是該放棄。** 只說「它在等」不夠,要把乘出來的數字一起送過去。

實際原因:`check-phase-status.ts` **每個 phase 列 spawn 一次 `npm exec cucumber-js`**,
38 個 phase = **38 次順序 spawn**,load 29 之下每次約 60 秒。

⚠️ **「被砍」和「38 個子行程」在對方那邊長得一模一樣 —— 都是不印東西。**
而區分它們的成本是一個 `ps`。**觀測方在別台/別的 session 看不到這個,持有機器的那一方要主動去量並送過去**
(那正是「發現自己有對方視角外的資料,不等問就送過去」)。

### ⚠️ 同一個東西有兩個名字:gate 名 ≠ npm script 名

實例:照輸出裡的 `gate=doc-links` 去打 `npm run check:doc-links` → `Missing script`。
**那支叫 `lint:docs`。**

**「用產物名當 import 表」那條把手,索引的是「文件與訊息裡的引用」,不是「可執行的入口」。**

兩個方向的失敗速度差很多,而**慢的那個才危險**:

| 方向 | 失敗速度 |
|---|---|
| 拿 gate 名去猜指令名 | **很快**(`Missing script`),所以便宜 |
| 拿 npm script 名去 grep 文件 | **很慢** —— 會**漏掉所有用 gate 名寫的那些**,而且不會有任何錯誤 |

> **掃引用的時候,一個產物可能有兩個名字(對外的 gate 名、對內的 script 名),兩個都要掃。**

這跟「按名字列的清單,漏掉的永遠是你沒想到的那個名字」是同一件事 ——
只是這次那個沒想到的名字,是**同一個東西的別名**。

### 兩張單還是一張單,分界是「會不會撞在同一行」

同日兩個看似相反的判斷,其實是同一條:

- **`--fail-fast` 那組併進 `adr-dup`,不開新分支** —— 因為它要改的是
  `gates.config.json` 與 `SKILL.md`,**跟那張正在改的是同一段**。分開會撞。
- **`learning/` 略過清單那件不併進去,排下一張** —— 雖然也在 `gates.config.json`,
  **但它動的是另一個鍵,不會撞在同一行**。

> **「同一段設定要合併」不等於「同一個檔案的所有事都要合併」。**
> 前者是為了避免衝突;後者會讓一張單失去驗收焦點,變成雜物袋。
> **分界是「會不會撞在同一行」。**

⚠️ 這條要跟「`git merge` 沒報衝突不代表合併對了」一起讀:
**git 的衝突單位是行,所以「會不會撞在同一行」正好是 git 幫不上忙的那條線。**
