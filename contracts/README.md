# contracts/ — 跨模組約定

平行開發的支點。十個功能要能同時開工,唯一的障礙是「A 需要 B 的型別才能動」。
把這些抽出來先定案,障礙就消失了。

## 兩層,鬆緊不同

v1.0 把整份契約都凍死了。那太重——TypeScript 型別改了編譯器會告訴你哪裡壞,
不需要走 ADR 這種儀式。v1.1 起分兩層:

### 硬約定(改動需要 ADR)

**磁碟上的東西**,因為模組之間實際上是靠檔案溝通的,而且改了會讓已產生的資料失效:

| 章節 | 內容 |
|---|---|
| §2 | 卡片 frontmatter 與 body 規則 |
| §3 | 考題檔格式 |
| §4 | reviews.json |
| §8 | deps.json / order |
| §9 | weekly.json |
| §10 | log 事件型別 |
| §11 | 設定檔 |
| §12 | 目錄結構 |
| §7 的 `LlmTask` 與路由表 | 三個模組共用的字串常數與行為約定 |

改這些之前先問:能不能不改?多數「需要新欄位」其實是模組內部的事。

### 軟約定(改了跑測試、更新這份文件就好)

**只存在於記憶體的介面**。改了編譯器會抓、測試會抓:

| 章節 | 內容 |
|---|---|
| §5 | `GradeResult` |
| §6 | 排程函式的輸入輸出 |
| §7 的函式簽章 | `call` / `probeOnline` / `probeLocal` |
| §13 | `LearningFs` |

規矩很簡單:改的人負責跑全部測試、更新這份文件、在 commit 訊息說一句為什麼。
不用 ADR,不用等確認,不用列重驗清單。

## 為什麼還是需要契約

你是一個人加 AI,不是十個人的團隊,所以契約的價值不在「治理」。它在兩件事:

1. **你可以挑任何一個資料夾開始而不被卡住**
2. **AI 在不同 session 之間不會偷偷漂移** — 這個更重要。沒有契約,今天寫的 `Review`
   和下週寫的 `Review` 會長得不一樣,而且要到整合時才發現

## 內容

| 檔案 | 內容 |
|---|---|
| `types.md` | 型別與檔案格式,標明硬 / 軟 |
| `fixtures/` | **真的測試資料檔案**,不是規範。直接拿來用 |

`types.md` 是規格,`01-data-layer/phase-1` 把它變成 zod schema。
在那之前其他功能照著手寫自己需要的型別,整合時換掉。這個短暫的重複是平行的代價。
