## 做法與為什麼

雜湊比的是磁碟上 `state/reviews.json` 的原始位元組,不是解析後再 `JSON.stringify` 的結果。排法不同、內容相同也要算被改過,測試有這條。檔案不存在用固定字串 `absent`,不用空檔的雜湊,這樣「這期間被人建了檔」才看得出來。

`loadReviews` / `saveReviews` 的簽章與函式本體都沒動。解析迴圈在 `readReviewsSnapshot` 裡照同一套 `ReviewSchema.parse` 重寫一份,不把 `loadReviews` 改成去呼叫新函式。既有呼叫端與測試依賴那兩個函式的現況,少碰它們比較不容易悄悄改行為。深度相等由受保護測試量。

`saveReviewsIfUnchanged` 在呼叫 `writeFileAtomic` 之前再讀一次。雜湊不同就丟 `ReviewsChangedError`,連暫存檔都不建。相同才用跟 `saveReviews` 一樣的字串(`JSON.stringify(reviews, null, 2)` 加一個結尾換行)寫入,回傳的是剛寫進去那份位元組的雜湊,不是寫完再讀磁碟——寫完到再讀之間別人又改,不該把別人的雜湊當成我們的基準。重讀比對到 rename 之間仍有微秒空窗,註解寫在 `io.ts` 的 `saveReviewsIfUnchanged` 上面。不加鎖、不改格式、不在 `learning/` 新增檔。`ReviewsChangedError` 從 `io.ts` 匯出;`session/index.ts` 本來就 `export * from './io.js'`,所以是同一個類別,沒有再抄一份。

`Session.reviewsHash` 是選用 `string`,沒有寫成可賦 `undefined`(`exactOptionalPropertyTypes`)。兩個建 session 的地方都記:

- `buildTodaySession` 改走 `readReviewsSnapshot`,把雜湊放進回傳的 session。函式本體不再呼叫 `loadReviews`。
- `scripts/review.ts` 的 `sessionFromCache` 同樣重讀並設 `reviewsHash`。快取格式 `SessionCacheSchema` 沒有加欄位(工單寫死:雜湊不落地、不進 ADR-074 快取)。續答時的基準是還原那一次讀到的,不是快取建立時的。

`submitAnswer` 只在「整張卡答完、要寫 reviews.json」那條路檢查。partial 與 `hadError` 維持不寫、不檢查。基準是 `session.reviewsHash`;沒設(手工組的 session,或測試把它刪掉)就用這次 `readReviewsSnapshot` 讀到的雜湊,等於退回現況的毫秒窗,既有測試不用改、也不放寬。不一致時在算轉移、寫入、`shift` queue、加 `passed`/`failed` 之前就丟錯。一致才算轉移,再交給 `saveReviewsIfUnchanged`(它會再比一次);成功後把 `session.reviewsHash` 設成回傳值,所以同一個 session 連答不會自己擋自己。丟錯之後這個 session 不可再用,core 不做復原。

終端機不在 `runInteractive` 裡接這個錯。`ReviewsChangedError` 一路丟到既有的 `main().catch`:印 `message` 到 stderr、退出碼 1。小結與 snapshot 寫在 `runInteractive` 之後,錯丟出來就走不到。另做一個專用 catch 再 `process.exit` 只是把同一件事寫兩次,而且容易在以後的改動裡先印小結再退出。`main().catch` 上面加了一行註解,標明這條契約。

沒有新增 `.ts`,沒有改 `scripts/boundaries.owners.json`。沒有改 `contracts/`、`prompts/`、`.feature`、帶 SOURCE 標頭的模板。不寫 ADR。
