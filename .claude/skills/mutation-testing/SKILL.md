# Mutation Testing

## 為什麼這個專案需要它

這個專案的核心是**間隔重複的排程邏輯**。排程算錯,使用者要幾週後才會發現,而且發現時已經記錯了一批東西。
一般的行覆蓋率救不了這件事——一個測試可以「執行」到 `stage + 1` 這一行卻不驗證結果,覆蓋率一樣是 100%。

變異測試的做法是:故意改壞程式(`+` 改成 `-`、`>` 改成 `>=`、把 `return true` 改成 `return false`),
然後看測試會不會失敗。測試失敗 = 變異被殺死 = 測試有效。測試照樣通過 = 變異存活 = **那行程式沒有被真正測到**。

## 什麼時候跑

| 時機 | 範圍 | 必要性 |
|---|---|---|
| 寫完一個模組的單元測試後 | 該模組 | 建議 |
| 驗收一個 phase 之前 | 該 phase 碰到的檔案 | **嚴格級必要,其他建議** |
| 整合之前 | 該整合涉及的模組 | 建議 |
| 修完 bug 之後 | 該檔案 | 建議(驗證新測試真的抓得到那個 bug) |

只有**嚴格級**是硬門檻(ADR-030)。標準級未達回報但不擋,由使用者決定要不要處理。
理由:嚴格級涵蓋了所有「錯了會靜默、幾週後才發現」的地方,其他的錯了很快就看得見。

不要每次存檔都跑。變異測試很慢——每個變異都要跑一次測試套件。

## 怎麼跑

```bash
npm run mutate                                          # 全部,慢
npx stryker run --mutate "packages/core/src/scheduler/**/*.ts"   # 單一模組
npx stryker run --mutate "packages/core/src/scheduler/interval.ts"  # 單一檔案
npx stryker run --incremental                           # 只跑變動過的,日常用這個
```

報告在 `reports/mutation/index.html`。

## 分級門檻

**不是所有程式都值得同樣的門檻。** 這個專案分三級:

| 級別 | 模組 | 門檻 | 理由 |
|---|---|---|---|
| 嚴格 | `scheduler/`、`grading/` 前兩層、字數與驗證器、`weekly-goal` 計數、路徑防護 | **95%,硬門檻** | 純函式或安全邊界,算錯的代價延遲數週才顯現 |
| 標準 | `ingest` 非 LLM 部分、`lint` 檢查、`llm-router` 路由決策、`review-cli` 的 session 邊界、`prompt-quality` 的結構檢查 | **80%,軟目標** | 有 IO 與外部依賴,部分變異難以合理殺死 |
| 寬鬆 | adapter、CLI 進入點、Svelte 元件、Tauri command、golden 的儲存與 diff | **不跑** | 邊界程式,由整合測試與 @manual 涵蓋 |

`stryker.config.json` 的全域 break 設 60,是最低防線,不是目標。判讀時用上面這張表。

## 怎麼判讀存活的變異

存活的變異**不一定是問題**。逐一分類,不要無腦補測試:

### 1. 真的漏測 → 補測試

最常見。例如 `overdueRatio` 的除法被改成乘法而測試沒失敗,代表沒有一個測試檢查了實際的比值。

**補的方式很重要**:補一個反映**真實需求**的測試,不是補一個剛好殺死那個變異的斷言。
問自己「如果程式真的這樣壞了,使用者會遇到什麼?」然後測那件事。

```
壞:expect(ratio).not.toBe(2)              // 只為了殺變異
好:expect(selectToday(...)[0].card).toBe('sec-0001')  // stage 1 逾期一天要排在 stage 5 逾期兩天前面
```

### 2. 等價變異 → 標記忽略

改了但行為完全一樣。例如效能相關的提前 return、防禦性的 null 檢查在型別上不可能為 null。

處理:在該行加 `// Stryker disable next-line all: <理由>`。**理由必填**,而且要說明為什麼等價,不是「測不到」。

### 3. 該行根本不該存在 → 刪掉

存活的變異有時候在告訴你這行是死程式。刪掉比補測試好。

### 4. 邊界條件沒測到 → 這是最有價值的發現

`>` 改 `>=` 存活,代表沒有測試踩在邊界上。這個專案的邊界特別多:

- body 剛好 100 字 / 101 字
- `daily_cap` 剛好等於到期數
- 逾期 0 天(當天到期)
- `fails_in_row` 剛好 2(觸發 reteach)/ 剛好 3(觸發 stuck)
- ISO 週的年末交界
- rubric 剛好 2 條 / 4 條

看到邊界變異存活,**優先處理**。

## 這個專案要特別注意的變異

### 排程間隔

`INTERVALS = [_, 1, 7, 30, 90, 180]` 的任何一格被改動,測試都必須失敗。
如果只有 `stage 1 → 2` 有測試,那 30 / 90 / 180 的變異會全部存活。用 `Scenario Outline` 蓋滿每一格。

### 逾期比例

這是 ADR-015 的核心,而且很容易寫出「看起來對」的錯誤實作。
除法改乘法、分子分母對調、用逾期天數取代比例——這四個變異都必須被殺死,
而且殺死它們的測試應該是「排序結果不同」,不是「數值不等於某個常數」。

### 字數計算

CJK 與非 CJK 的判斷式、標點的排除、example 圍欄的排除。
每個條件分支的變異都要被殺死,而且要用真的卡片內容測,不是用人造字串。

### session 邊界(review-cli)

「今天的題目一旦決定就固定」「答案每題立刻落地」「跨日重建」——
這三個的條件判斷被改壞時,測試必須失敗。特別是「已答過的不再問」的守衛:
那個變異存活代表 session 重建時可能重複問同一張卡。

### 審核的三層短路

`exact → fuzzy → llm` 的每個提前 return 被移除時,測試都要失敗。
特別是「第一層命中就不該呼叫 LLM」——這個變異存活代表你沒有測到成本控制的行為。

## 不要做的事

- **不要為了衝分數寫斷言。** 分數不是目的,測試有效才是。為了殺變異而寫的斷言會在重構時變成阻力。
- **不要對 UI 元件追高分。** Svelte 元件的變異多半沒有意義,那是 `@manual` 場景的地盤。
- **不要在 CI 每次 push 都跑全量。** 用 `--incremental`,或只在整合前跑全量。
- **不要用 disable 逃避。** 每個 disable 都要有理由,而且理由要能說服三個月後的自己。

## 回報格式

跑完之後這樣回報:

```
變異測試:<範圍>

分數:X%(門檻 Y%,級別:嚴格 / 標準 / 寬鬆)
變異:總 N,殺死 A,存活 B,逾時 C,無涵蓋 D

存活變異分類:
  真的漏測:n 個 → 列出檔案:行,以及該補什麼測試
  邊界未測:n 個 → 列出,優先處理
  等價變異:n 個 → 列出,建議加 disable 註解與理由
  死程式:n 個 → 列出,建議刪除

判定:通過 / 未通過(門檻)
下一步:...
```

未達門檻時**不要自動補測試**。先列出分類,問使用者要處理哪些。
補測試是設計決策,不是機械動作。
