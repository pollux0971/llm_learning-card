## 產物與環境

- 建置(協調者給的重活位子,`CARGO_BUILD_JOBS=2`):2026-10-23 16:15:28–16:15:38 在 `d3a1da7` 跑 `npx tauri build --debug --no-bundle`(`../../apps/desktop`),exit 0,cargo `Finished` 6.07s。執行檔 183224128 bytes,sha256 `75df48340cb6292b285c4213bcc8f81abd26d37379ea80c5f857931aa44bd30a`。建置產物的考試卡 js 裡有「還在準備」字樣、教學卡 js 裡有 `prereq-label`(各 1 個檔)。
- **全部在隔離的顯示裡**:`Xvfb :97` + 巢狀 `gnome-shell --x11`(GNOME Shell 46,`dbus-run-session` 起私人 session bus;`HOME`、`XDG_*` 全指暫存根)。沒有在使用者的桌面 `:1` 開視窗、沒有對 `:1` 送任何輸入。
  - **記憶體上限**:Xvfb 與巢狀 session 各包一個 `systemd-run --user --scope -p MemoryMax=… -p MemorySwapMax=0 -p TimeoutStopSec=10`(Xvfb 1G、巢狀 session 2G),實測 scope 的 `MemoryMax` 是 1073741824 與 2147483648、`MemorySwapMax` 0。
  - **上限被撐到兩次(16:19:49、16:23:47)**:巢狀 session 帶起來的 ibus-daemon 約 70 秒就漲到 1.87 GB,kernel 在那個 scope 裡把它 OOM 殺掉(`oom_memcg` 指的是巢狀 session 的 scope);使用者桌面自己的 ibus-daemon 沒動。被殺之後 systemd 把整個 scope 收掉,巢狀 shell 與私人 session bus 都沒了;app 的 session bus 連線斷掉時,GLib 自己送 SIGTERM 給自己(那兩次 app 結束碼 -15,不是收工程式送的)。之後那批剩下的幾次是在沒有視窗管理員的情況下跑的,所以**那兩批(各 12 次)整批作廢**,不算進任何數字。作廢的兩批裡也沒有出現「複習程式停了。」或 `bad-envelope`。

### 三側一起量

- **側車那一側**:`PATH` 最前面放一個 `node` 替身,只在參數有 `review-sidecar.ts` 時介入,記側車 stdin / stdout 每一行的時間、`id`、`method` 或回應種類(不記內容)。Rust 換過號,所以這裡看到的是**線上 id**。慢側車那幾批由替身把側車的 `hello` 晚 2 秒或 3 秒才交給 Rust(Rust 在鎖裡等 `hello`,所以第二個視窗的 `busy` 一定超過 1 秒)。
- **視窗那一側**:一支量測程式用檢查器同時接上兩個頁面(WebKitGTK 一頁只能接一個前端,操作也由它做),開 `Network` 記每一筆 review IPC 的 webview `id`、`method`,以及回應內容裡的 `id` 與錯誤種類。每個視窗最早那一兩筆常常比它早,那幾筆只在側車那一側看得到。
- **畫面那一側**(這次新加):一接上就在兩個頁面各裝一個 `MutationObserver`,DOM 每變一次就記一筆畫面狀態(捲動區的字、等候字樣、錯誤字樣、停用的按鈕)。所以「有沒有出現過『複習程式停了。』」「有沒有出現過英文 kind」看的是**每一個畫面**,不只最後停在哪裡。比對英文 kind 用的清單是 `../../packages/core/src/session/protocol.ts` 第 41 行起 `ERROR_MESSAGES` 的 21 個 kind。
